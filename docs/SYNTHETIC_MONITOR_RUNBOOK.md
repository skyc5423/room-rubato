## Schedule definition for root

Integrate with the root's **existing November 18 checks at 12:55, 13:05 and 13:15 UTC**. Do not create duplicate schedules. Root also has a November 23 closure check. No recurring daily schedule is asserted installed here. On any wake at or after `2026-11-24T00:00:00.000Z`, do no collection/write and stop; do not extend the pilot automatically.

Use **59-minute** lookbacks, not 50: at 12:55, a 50-minute window misses 12:00–12:04 Cron runs. The three existing check times with 59-minute lookbacks cover every minute of today's nominal Cron window in synthetic tests. One-hour requests can fail at the Hobby retention boundary, hence the one-minute margin. A first wake delayed more than roughly four minutes can lose the earliest evidence: treat delayed/missed coverage as a monitor coverage gap, not Cron failure. Subsequent days require a separately confirmed existing wake; today's three checks do not imply continuous monitoring.

At every wake:
1. Check actual UTC time and current writer project metadata. Expected project/deployment are held in private root context; do not silently follow a different deployment. Verify plain env gates remain synthetic-only and production disabled, and expiry has not changed. Do not decrypt or copy any sensitive env values.
2. Query `get_runtime_logs` with the approved writer project/team/deployment, `environment=production`, `since=59m`, `query=RUBATO_SYNTHETIC_PILOT_`, `limit=100`. Save the exact response privately for offline parsing. Inspect tool success/error explicitly. Classifier requires 58–59 minutes of returned coverage (one-minute tolerance) and a response ending no more than two minutes before the check; shorter/stale windows are invalid monitor evidence, not a missing backup. Do not merge responses with multiple Markdown headers or select around a reported diagnostic failure. Truncated/ambiguous/malformed results fail closed.
3. Use `classifySyntheticLogCheck` for the same UTC day and observed check time. It validates source labels, response coverage, complete receipt/chunks, digests and fixture envelope through the existing evidence parser. Its result never certifies restore, current Blob availability, HMAC authenticity or production readiness. Even authenticated connector logs can be forged by a compromised writer/account; hashes are consistency checks, not independent signatures.
4. Insert only the allowlisted metadata fields, including validated `coverage_from`/`coverage_to` into the private observation table using `event_id` conflict protection. Reuse the same event ID on retries; never interpolate raw log text/errors. Re-read the event and permissions as needed. Coverage timestamps are persisted; a DB constraint rejects non-null windows outside 58–59 minutes (one-second upper tolerance). If storage fails, report monitor persistence failure rather than losing the observation silently. Do not query Vault or user tables.
5. Before the 13:10 deadline, absent logs are `waiting_window`. At or after the deadline, read **all preserved observations for the day**: a previously saved complete-artifact observation means later empty overlapping windows do not erase that evidence. Without one, absence is missing evidence, not confirmed cron failure. Invalid evidence/connector failures remain separate faults even if an earlier artifact exists.
6. Notify the user in the existing verified private chat only for newly observed diagnostic/monitor/persistence failure, missing evidence after deadline, or a material recovery update. Wording must say synthetic evidence/monitoring, never real-data backup failure or successful recovery. No routine pre-window empty-log message. Suppress duplicates using durable claim/receipt state or verified messaging history; never blindly retry uncertain sends. Root resolves the actual conversation, sends, and checks its tool receipt. Do not create a new recipient/channel/webhook.
7. Complete artifact without an independent successful decrypt/PGlite restore remains `evidence_unverified`, not a failure-free backup certificate. Do not send repeated daily “restore unverified” alerts if the root has already explained that known missing gate and nothing changed.

The local file outbox supports send reservation/reconciliation, but its storage has not been replaced by this hosted observation table: the table currently stores monitor observations, **not durable chat claims/receipts**. Root must use verified messaging history for deduplication until a reviewed hosted claim adapter exists. Exactly-once human delivery is not claimed.

## Limits and evidence

This setup persists only small fixed-code synthetic monitor observations outside the Vercel writer. It cannot survive loss of the shared Supabase account, guarantee connector sessions remain authorized forever, establish full log coverage after scheduler outages, prove present Blob retention, or perform a production-data backup. Full incident-delivery integration, source authentication recovery, watchdog and actual matching-key restore remain explicit gates.
